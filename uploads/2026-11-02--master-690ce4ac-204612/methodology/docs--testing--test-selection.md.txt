# 回归测试分层选择

逐 Case 资格、机制覆盖和正式流水线状态分别记录，最新结果见[台账](../../test/e2e/cases/README.md)。E2E 通过不能覆盖 Core 失败。单元／集成／端到端是测试层级，与硬判定、失败分析、人工复核不是同一概念。

本文只回答：一个风险需要哪层测试，以及网页测试该选 live 还是 deterministic。选好以后按[新增 SOP](new-playwright-case-sop.md)实现；题面、断言和稳定性标准见[设计准则](case-design.md)。

## 1. 三层的职责边界

| 层 | 位置 | 运行形态 | 证明什么 | 不证明什么 |
|---|---|---|---|---|
| 单元 | 通常在`test/unit/*.test.ts` | node:test，直接调用模块；纯逻辑测试不依赖网络、子进程或真实模型 | 单个模块的输入输出契约：解析、校验、状态转移、数据变换、提示词构建 | 跨模块协作、真实进程、UI 投影 |
| 集成 | `test/integration/*.test.ts` | node:test，组装真实 Kernel/Host/SQLite，可用确定性模型服务与回环代理 | 多组件协作契约：Policy 仲裁、ToolRuntime 调度、持久化恢复、竞态、进程生命周期 | 用户在真实 UI 中的自然任务、真实模型规划 |
| 端到端 | `test/e2e/`（Playwright） | 真实浏览器 + 真实 Web Host + 真实 SQLite，模型来自确定性替身或真实 Provider | 从 Web UI 发起的自然用户任务中，机制作为完成任务的必经路径实际发生，且页面、SQLite、工作区三层事实闭环 | 被测机制之外的其他能力；确定性通路不证明真实模型能力 |

三层的判定断言必须始终对应可观察行为（仓库约定，见 `AGENTS.md`）。低层测试负责定位失败原因，高层测试负责证明产品语义没有被破坏；高层不能因为"低层已经测过"而放宽断言，低层也不能因为"反正 e2e 会跑"而缺席。历史文件位置不等于证据层级：例如`test/unit/standard-tools.test.ts`中有真实子进程控制，`core-service-runtime.test.ts`中有SQLite重开恢复；这些具体测试应按集成证据记录，不能仅凭unit目录称为纯单元测试。

## 2. 判定框架

新增或修改机制时，逐项回答以下问题，命中的层级需要累积，不能在第一个层级停住。例如新 Tool 通常同时需要单元和集成测试；如果它还是自然用户任务的必经能力，再增加 Playwright Case。

```text
Q1 是否涉及跨模块协作：Kernel 主循环、Policy 仲裁、Tool 调度、
   子 Agent、持久化与恢复、进程生命周期、并发竞态？
   ├─ 否 → 继续 Q2
   └─ 是 → 增加集成测试，并继续 Q2

Q2 是否包含可独立验证的模块内逻辑，可用普通函数调用触发并观察？
   ├─ 否 → 继续 Q3；若任何层都无法观察，先重新设计可观察边界
   └─ 是 → 增加单元测试，并继续 Q3

Q3 失效是否需要通过真实 Web UI 中的用户任务才能完整暴露，
   或该能力本身就是产品级用户语义？
   ├─ 否 → 单元/集成层已经足够
   └─ 是 → 增加 Playwright Case，并按 2.1 选择 live 或 deterministic
```

### 2.1 什么时候需要 Playwright Case，如何选择 live 或 deterministic

live 全量会持续数小时并消耗真实模型样本，因此“可以写 Case”不等于“应该写 Case”。同时满足以下条件才立项，并用第 4 条选择模型通路；取样门槛见[设计准则](case-design.md#5-什么叫稳定什么叫全量通过)。

1. **机制已在 `mode.yaml` 激活并被 Host 绑定**。Contract 兼容预检会拒绝装配缺失的 Case，所以先确认 `config/modes/<mode>/mode.yaml` 已选择该 Tool/Policy。
2. **失效模式具有用户可感知的产品语义**：错误的页面投影、刷新后丢失状态、错误的授权或副作用、跨层不一致（页面说的和 SQLite 记的不同）。只影响内部日志或非核心元数据的缺陷不需要 Case。
3. **机制是完成某个自然用户任务的必经路径**：存在一个真实用户会提出的任务，不经过该机制就无法完成。如果只能靠题面塞入 `HISTORY-BEGIN`、内部事件编号之类的观察者暗语才能触发，这是 Case 设计问题，不能立项（见[题面要求](case-design.md#2-题面和断言必须说同一件事)）。
4. **模型通路与验证目标一致**：需要证明模型能从自然题面选择目标机制、消费真实结果并完成任务时使用 live；需要稳定制造 Provider 错误、协议异常、恢复或其他正常用户难以复现的兜底条件时使用 deterministic。确定性输入能够触发某条路径，不等于可以省掉正常用户路径的 live 覆盖；反过来，deterministic 通过也不能冒充真实模型能力覆盖。

真实模型能稳定触发的正常路径优先放在 live，不因为脚本更快、更容易通过就再复制一份。确定性立项要指出额外制造的异常或边界，例如服务恰在审批中断、模型传入不允许的执行参数；只有“调用某工具并返回结果”不足以立项。发现已有候选不符合这个分工时，转入 live 候选或低层测试，不为凑满一批而保留。

缺陷定性同样先看用户后果与设计契约。018缺少内部来源字段，但尚未证明执行、取消或分叉错误，已撤销原定性；不能为补字段强行新建Playwright。047用生产调度服务复现“删除成功后又投递”，本次已用永久集成控制锁定并修复该时序；是否增加网页Case仍依据尚未覆盖的交互后果，不把服务级通过当成网页资格。真实计时器不等于真实Web验收，临时诊断也不计入已注册Case数。

### 2.2 Q1/Q2/Q3 的典型落点

| 变更类型 | 单元 | 集成 | Playwright Case |
|---|---|---|---|
| 纯函数、Schema 解析、参数格式构建（如 `common/tool-definition`） | ✅ 必须 | 一般不需要 | ❌ |
| Policy 的内部状态机、提示词构建、领域存储读写 | ✅ 必须 | 持久化/恢复路径需要 | 仅当构成用户任务必经路径（如记忆写入-召回） |
| Tool 的执行语义（校验、超时、取消、副作用） | 校验逻辑 ✅ | 执行约束、取消、进程清理 ✅ | 用户任务中真实调用并核对三层事实时 |
| 跨 Policy 仲裁、Kernel 状态转换 | 单领域部分 ✅ | ✅ 必须 | 关键转换（interrupted、compaction、turn 推进）已有对应 Case，修改后必须复验 |
| Web UI 投影、刷新恢复、会话管理 | 纯展示逻辑 ✅ | manager 层协作 ✅ | 投影正确性与刷新闭环本身是用户语义 → 现有 Case 已覆盖的必须复验 |
| Provider 适配、模型协议、代理行为 | 协议解析 ✅ | 用确定性模型服务实测 ✅ | 基础连通性由 `standard.infrastructure-smoke` 承担 |
| 故障注入（Provider 500/429、截断、断连） | 解析容错 ✅ | 能稳定模拟的部分 ✅ | 属确定性通路职责；已注册故障Case、逐项资格和剩余边界见台账，不能把注册等同于通过 |

### 2.3 修改现有机制时的判定

修改分为三档，各档要求不同：

1. **契约不变的实现重构**：保持现有测试全绿即可；不新增 Case。
2. **行为变化但契约不变**（修 bug、放宽/收紧内部边界）：先用规范和实现定位差异。断言误读契约时修断言；断言正确而实现违约时修实现，不能改测试掩盖产品问题。若变化触及任何已注册 Case 的必经机制或判定语义，该 Case 视为实质修改，旧成绩只作历史，必须按[新增 SOP](new-playwright-case-sop.md#6-要登记稳定成绩先固定版本)重新取样。
3. **新增行为或新契约**：回到第 2 节从 Q1 开始判定。

任何情况下，`src/kernel/**` 与 `spec/**` 的改动须先获得人工确认（见 `AGENTS.md`），该确认不因测试工作而豁免。

## 3. 选好以后做什么

把风险、所选层级及不覆盖范围写进设计单，按[新增 Playwright Case SOP](new-playwright-case-sop.md)完成代码、单项验证和台账。若无需网页 Case，直接为对应产品模块补有意义的单元/集成验证，不为凑数增加 Case。

套件与产品修复分支如何分工见[总体方案](harness-evaluation.md#4-分支与交付方式)：Case 合入 `devops/luoshijie02`；产品修复及其必要低层测试单独向 master 交付。
