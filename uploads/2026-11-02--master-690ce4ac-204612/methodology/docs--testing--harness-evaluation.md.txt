# LongCat Harness 回归评测总体方案

本文只维护阶段目标、建设现状和后续方向。文档分工见[文档入口](README.md)，逐 Case 成绩见[台账](../../test/e2e/cases/README.md)，产品行为以 [spec](../../spec/README.md) 为准。

## 1. 要解决什么问题

用从真实 Web UI 发起的用户任务，持续判断 Harness 的功能是否发生回归。关注 Tool、Skill、Policy、Mode 装配、Host、Provider、权限、消息与持久化、子 Agent、后台任务和界面投影；不把 Case 数量或工具出现次数当架构覆盖率。

每个 Case 只验证一个清楚的核心机制和必要组合。范围由已注册 Case、实际证据和明确的未覆盖项共同表达，不再维护另一份固定数量的机制清单。

## 2. G1、G2、G3 分别做到哪里

| 阶段 | 目标 | 当前已实现 | 仍需区分的边界 |
|---|---|---|---|
| G1 功能回归 | 验证自然任务、关键故障、取消及恢复中的功能正确性 | 两路 Playwright、隔离服务、Contract/Driver/audit、持久事实与业务真值闭环、冻结与补样、周实验及报告入口 | 建设完成不等于当前 master 全量 PASS；最新单项资格、失败和待处理项只看台账及对应冻结实验 |
| G2 消息结构 | 用一份融合规则检查最终模型消息结构，并定位受影响的组装代码 | 规则正文、源码映射、轨迹检查、Git 溯源、Codex 只读裁判及周入口后处理 | 基线仍待人工 review；未触发不要求补齐 Case，已触发但缺证据必须说明；不自动豁免 G1 失败 |
| G3 扩展性 | 验证新增 Mode/能力组合能否遵守扩展边界 | 当前作为后续方向 | 尚不宣称已建立并通过独立的 G3 验收体系 |

G2 只维护[一份规则](../../scripts/evaluation/g2/rules.md)：限定角色、顺序、位置、包含关系和调用关联，不按 Mode 重复建库，不固定提示词文案或业务值。每条有具体源码依据，动态轨迹核对实际请求；规则与代码变更是否合理仍由人审查。运行和证据边界见 [G2 手册](../../scripts/evaluation/g2/README.md)。

G1 的硬判定、失败证据分析和人工复核各有职责：分析层已经有方法和报告入口，但不能把“归因为上游”自动改成 PASS。完整自动裁判替代硬判定、自动豁免失败不属于当前已交付能力。

## 3. 两条执行通路

两路都用真实浏览器、Web Host、Kernel、Policy 和 SQLite；触发 Tool 时执行真实工具。差异在模型来源。

| 通路 | 用途 | 不证明什么 |
|---|---|---|
| live，真实模型 | 自然题面下选择机制、消费真实结果并完成业务 | 未发生的机制、任意模型或所有合法路径 |
| deterministic，受控模型服务 | 稳定制造 Provider 错误、截断、拒绝、崩溃、取消和恢复等条件 | 真实模型能否自主规划正常任务 |

`standard.infrastructure-smoke` 检查浏览器、协议、服务、SQLite、刷新和产物链路，不计业务机制覆盖。其他 Case 的精确协议和资格在源码及台账维护，不在这里复制数量和逐项成绩。

单元、集成、网页测试按风险累积选择。内部逻辑已有低层证据就不机械加网页 Case；具体判断看[测试分层选择](test-selection.md)。题面/断言、稳定性门槛见[设计准则](case-design.md)，接入步骤见[新增 SOP](new-playwright-case-sop.md)。

## 4. 分支与交付方式

**回归套件长期放在 `devops/luoshijie02`，不整体合入 master。** Case、评测自检、流水线、G1/G2 配套方法文档随套件维护。维护者从最新 `origin/devops/luoshijie02` 切工作分支，完成 Case 与验证后向 `devops/luoshijie02` 提交 PR；不要把 Case PR 的目标误设为 master。

实验发现的 LCH 产品缺陷另开修复分支，以最新 `origin/master` 为基线，只带必要产品修改、相关单元/集成/Web UI 产品测试及缺陷说明，再向 master 提交 PR。不为减少 master 体积省掉产品修复本身所需的测试，也不把整套 Playwright Case 带过去。Kernel/spec 的具体改动仍须事先授权。

评测分支按需要同步已合入 master 的产品变化并检查兼容；不用它长期承载另一套产品实现。已有但未合入 master 的修复在台账明确标为集成缺口。不要反向将整个评测分支合到 master，也不要用套件分支上的产品补丁修饰 master 的评测结果。

周入口分别冻结最新远端 master、已提交 suite 和实际 evaluated tree，只覆盖登记的评测文件。产品源码、配置、规范、依赖及清单外产品测试保持 master；准确覆盖清单与命令见[运行手册](../../scripts/evaluation/README.md#31-每周评测远端-master)。套件与新 master 不兼容时报告准备/收集/构建阻断，不静默换成旧 Case 子集或合入产品补丁。

另一台机器需要取得套件分支及溯源所需 Git 历史，配置锁定工具链、Provider 凭据、Codex 裁判和本机调度。默认 suite 是**本地已提交分支头**，不是每次自动更新远端 suite；维护者先按评审结果更新本地基线。master 则由周入口每次 fetch 冻结，即使未变化也独立采样。

## 5. 如何理解成绩与证据

“单项稳定”“某次全集原始成绩”“正式门禁”分开报告。新源码、Mode、模型、配置或断言不能继承旧资格，不拼接历史 PASS；Core 失败不能被网页成功覆盖。取样标准只在[设计准则](case-design.md#5-什么叫稳定什么叫全量通过)维护，归因和报告方法只在[失败归因指南](failure-attribution.md)维护。

每次报告以本次冻结事实为准，首页概括数量和结果，正文集中全部失败 Case；成功明细及逐样本数据放 JSON。发现问题不自动等于已修复，已修复也不自动等于进入 master 或完成复验。

所有实验用独立随机端口、工作区和状态目录，不操作 8088，不复制日常状态库。凭据显式映射并脱敏；源码归档、日志及轨迹保留在仓库外。进程隔离不等于恶意代码沙箱，不在含密钥的可信评测环境直接执行未经审查的外部代码。

## 6. 尚未覆盖的边界与后续工作

- 已登记正常路径和故障样本不等于任意跨宿主竞争、全部崩溃窗口、所有 Provider/第三方扩展均正确；未激活或未绑定能力不计覆盖。
- 主请求轨迹完整不等于副模型请求完整；通用 completion 服务尚未保存完整 messages 的路径仍是 G2 证据缺口。非空 persona、多模态等未触发路径可以保留源码依据，不为单次报告强制加 Case。
- 继续处理台账中有证据的 Case/产品问题；已有模型质量问题按当前范围只登记，不为提高通过率放宽核心断言。
- 套件迁移后先验证最新 master 与 suite 的兼容、凭据和产物链路，再启用每周一 00:00（Asia/Shanghai）调度并验收完整报告。调度由新机器配置，仓库代码不会自动创建任务；本机任务已按用户要求停用，不因更新文档恢复。
- G2 基线由维护者 review，再处理真正的结构违反、组装代码影响和已触发的证据缺口；G3 另行确定范围与验收场景。
