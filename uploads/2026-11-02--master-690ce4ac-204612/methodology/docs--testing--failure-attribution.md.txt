# 失败 Case 归因指南

这份文档集中维护归因方法：先证明发生了什么，再判断哪里错、谁适合跟进。适用于单项调试、G1 全量和周实验；不替代产品 [spec](../../spec/README.md) 或正式判分。Case 设计与取样标准见[设计准则](case-design.md)，命令和产物路径见[运行手册](../../scripts/evaluation/README.md)。

## 1. 开始前先固定对象

先保留原始失败，不重跑覆盖、不改旧附件。阅读 AGENTS、相关规范/验收场景、Case 台账、实际 Contract/Driver/audit，以及问题域的 Bug 文档；安装了 `lch-web-regression` 时也要阅读。桌面结构 Bug 汇总只能提供线索，不能替代本次源码和证据。

| 对象 | 必须确认 |
|---|---|
| 产品 | 本次 master SHA、实际 evaluated tree；不能拿 devops 的产品补丁解释 master |
| 评测 | suite SHA、Case/共享审计/fixture/runner；包括旧 ID 和改名文件 |
| 配置 | Mode 与 binding、模型/Provider/revision、参数、预算、工具链、浏览器 |
| 样本 | profile、caseId、原始/替补/专项样本、repeatEachIndex、retry、真实目录 |
| 完整性 | JUnit、audit/timings、失败诊断、服务日志、trace、trajectory、清理状态 |

独立运行的第六样本可能也使用 `repeatEachIndex=0`，必须用目录和计划里的样本位置区分，不能只按 index 合并。已有网络补样不得丢掉原始失败。规范、实现现状和历史成绩分别记录。

## 2. 先还原用户合同，再找第一处分歧

把每轮题面原文、用户目标、最小夹具、独立真值、必经机制、允许变化、时间预算及不覆盖范围写出来。逐项对照实际 Tool Schema、Policy、Mode 和结果渲染代码；**不能凭工具名称猜参数或效果**。

同时核验题面里的限制是否必要。题面和断言一致，仍可能共同增加与业务、核心机制无关的要求；不能看到模型违反了题面，就直接归为模型问题。必要性的判断与正反例统一见[设计准则](case-design.md#每条强制断言都要有必要性依据)。

先选一个观察结论，暂时不要急着定责任：

| 机制状态 | 下一步 |
|---|---|
| 没触发 | 查题面是否使它成为必经、装配是否激活、前置审批/错误、其他合法路线、审计盲区 |
| 触发了，但执行、业务、消费或恢复错误 | 找到从正确输入变成错误结果的最早一层 |
| 机制和业务正确，却被评测拒绝 | 查 Driver、断言、oracle、等待条件和表示层比较 |
| 无法确认 | 明确缺哪份证据，标待复核，不推断模型上界或产品覆盖 |

沿实际因果链读取：

```text
自然题面和 UI 动作
→ HTTP/Host 接收
→ 实际模型请求与响应
→ tool.call / 权限 / tool.dispatch.started
→ tool.raw_result / 选中的 Policy 效果 / tool.result
→ 耐久消息与事件
→ 后续决策实际消费
→ 文件、服务等独立业务真值
→ 页面、详情及刷新
```

这不是要求每个 Case 都有所有节点。没有 Tool 的 Provider 重试 Case 查模型与状态链；嵌套工具按实际 service/call 协议查，不能硬套直接工具的 dispatch 形状。具体字段和公共审计入口见[技术方案](web-regression.md)。只读 HTTP、SQLite 用于观察，不用它们替代用户提交或写业务状态。

第一处分歧必须写成：“预期 X，实际 Y，在某请求/事件/代码处首次不同，因此导致 Z”。最早出现的任何 error 不一定是主因：参数拒绝已经恢复，最后却被固定调用次数误拒，主因就在断言；早先已恢复的断网也不能解释后来的错误写入。

辅助模型错误要再区分两种情况：同一请求重试成功，或策略记录失败后按既定行为继续主任务。后者不能写成“辅助模型恢复成功”。若辅助功能不是本 Case 的验证目标，且真实失败、持久化错误状态、合法继续路径和完整业务/UI 验收都能证明，可以将其作为诊断保留；不能仅凭最后文件正确就放行。`started + failed` 也是完整的服务调用记录；只有开始而没有完成或失败才属于未决。具体可接受范围和硬性检查见 [Web 审计规则](web-regression.md)。旧样本因审计提前退出而没执行完后续验收的，仍保留原 FAIL，修正后另冻结取样。

## 3. 分类：逐失败样本给主因

一个 Case 可以有不同原因的失败样本。每个样本只计一个主因，次因单列，不互相抵消；证据不足就待复核。

| 类别 | 什么证据支持它 | 应给出的处理 |
|---|---|---|
| 题面/覆盖/夹具设计 | 隐藏要求、材料不足、断言强于题面、合理路径绕过目标、组合太重 | 简化、拆分、补齐明确需求，保留核心机制与独立真值 |
| 断言/Driver/audit | 合规业务被固定次数/顺序、错误 oracle、选择器、时序或解析拒绝；或错误被漏判 | 修正具体误读，补相关正反控制，另冻结复验 |
| 无关强制要求（上述两类的子类） | 删除该限制不会放过业务错值、目标机制缺失或契约违约，却因固定格式、参数、次数或中间路径判失败 | 题面也强加限制时归 Case 设计；只有审计加门槛时归断言设计。记录具体断言及缺少的必要性依据，题面/断言一起复核 |
| LCH 结构缺陷 | 合理任务和合法动作已到达产品，但具体实现违反规范/公开契约 | 指明代码、条款、用户影响、修复与单元/集成/Web 正反验证 |
| master 集成缺口 | 已有修复未进入被测 master，实际错误逻辑仍存在 | 属产品问题子类，核对修复与等价补丁，建议独立集成 |
| 上游模型/服务 | 实际响应有空正文、污染、非法参数、选路偏离等，且产品处理链无相应错误 | 只写到证据能证明的层；现阶段已登记模型问题暂缓修复 |
| 网络/网关/机器外因 | 外部条件有直接证据，未恢复且确实阻断本样本 | 区分原因与补样资格，保留失败和映射 |
| runner/证据问题 | 收集、安装、构建、执行器、附件或取证失败 | 指明阶段及实际未执行范围，不报成模型或业务失败 |
| 待复核 | 证据缺失或不能区分多个解释 | 列缺口与下一步，不虚构代码作者 |

“模型能力上界”比“这次输出错误”更强：必须排除 Case、产品、Provider 和环境因素，并有同树固定配置下的重复证据。单次没选中工具、超时或答错，不能证明上界。前端报错名称、HTTP 状态、最终答案也都不能单独决定分类。

“无关强制要求”不单独重复计数，不是自动豁免。静态发现限制多余，只能证明存在设计缺陷；归因某个失败样本，还须核对它是否真的卡在该断言，以及是否存在更早的业务错误。两个模型都 0/8 只能促使重新审查，不能替代证据。真实非法参数、空响应或未完成任务仍按各自证据登记，不能被 Case 问题覆盖。

## 4. 判断断言是不是靠猜写出来的

拿实际合规结果反查契约，而不是按一次结果定制通过条件：

1. **先核对要求是否必要，再核对题面强度。** 对每条硬断言写清“删除它会放过什么具体错误”。11×11 必须是 121；指定文件字节必须一致。仅为解析方便增加的纯文本、固定行数、参数写法或调用总次数，即使写进题面也不自动合理。必要要求须在对应那轮题面明确表达。
2. **核对真实工具。** 参数是不是 Schema 真有的字段？结果是文本、结构化值还是经 renderer 转换？工具是否本来就允许分片、重复读取或同值设置？例如后台 Bash 的 `async_launched` 只是启动回执，须关联同一任务的真实 TaskOutput 终态，不能猜成 `running` 或直接当作完成。
3. **区分调用、执行和业务副作用。** 第一次参数拒绝且零派发，修正后唯一创建，可以合规。同一调用重复派发不能豁免；不同合法调用修正同一目标文件，不等于重复通知或重复付款。逐次核对真实工具语义、权限、源文件和最终交付，不能只看总次数或只看最终文件。
4. **区分原始结果和最终投影。** 内容改变必须有选中的效果、真实调用身份和完整投影链；raw/final 互相相等也可能共同错绑。
5. **证明实际消费。** 正确值存进 SQLite 不代表目标模型请求看到了它；检查具体决策请求、来源和完整内容。最终碰巧答对不够。若 Policy 合法追加了提醒，应按请求前已提交的追加记录和哈希还原消息投影，保留完整原工具内容；不能要求投影仍逐字等于初始结果，也不能用子串匹配忽略未归因的改动。
6. **检查页面时序和表示。** completed 可能先于页面正文到达；后台委派可有过程报告。运行中快照可能正好遇到末尾一个模型请求尚未返回，不能套用终态的“全部请求已有结果”；更早结果丢失、多个未结束请求和已结束轮次缺结果仍须拒绝，最终收尾继续逐请求完整对账。用原绝对 deadline 等当前业务报告，按真实 Markdown 渲染核对全文与刷新，不只抓一个 marker。
7. **补反证。** 接受合法新路径的正控，同时拒绝错值、冲突、缺机制、未消费、错身份或重复副作用。控制必须真的到达目标断言，不能把夹具 UTF-8 损坏或前置失败当有效反控。

断言修正后，历史样本只能用于解释和反事实回放，不能自动升级成新版资格。其他独立失败仍保留。涉及共享审计时，复用当次生产解析/渲染契约，不维护另一套过时规则。

以下是已经遇到的具体区别，后续样本仍须独立取证：

| 现象 | 可以支持的判断 | 不能据此放过 |
|---|---|---|
| 监听设置保护期限，但取得消息后主动关闭 | 若首个拒绝点是 `timeoutMs === 0`，核对是否为无关强制要求；应检查同一任务、真实消费、关闭因果及到期前停止 | 自行到期后补停、没读到消息、错误任务或遗留连接 |
| PTC 首次计算有误，之后读取真实数据并修正文件 | “只写一次”不是文件统计交接天然具备的业务要求；检查最终交付链，而不是单凭两次写入归模型 | 硬编码、最终错值、源文件损坏、越权写入、同一调用重复派发 |
| 压缩摘要用「字段：正确值」却报错值 | 若原文、完整值及消费链正确，应查字段边界解析；正常引号不是污染 | 错误姓名、截断版本、冲突记录、没有替换或没有实际消费 |

记录时保留：本例核心目标、被拒绝的具体要求和源码行、必要性依据是否成立、实际轨迹、独立错误、建议修订及正反验证。若旧审计提前退出，后续 UI/刷新没有完成，就仍保留原 FAIL；修正要求后重新冻结取样。

## 5. 网络、429、长尾与补样

分别回答三件事：发生了什么外部条件；它是否直接导致失败；它是否满足冻结分类器的作废条件。这三个答案不能互相替代。

- 查上游状态与本机代理封装状态、requestId、响应头/首块/结束时间、字节、内部恢复、最后未恢复请求，以及 Turn 终态或 Playwright 报错。排除已独立成立的业务/机制/断言失败。
- 本机代理返回 502 不证明上游返回 5xx。读取 `causeCodes` 和来源；实际门槛以本次冻结的 `failure-diagnostics.ts`、`live-model-proxy.mjs`、`retry-external.mjs` 为准。
- DNS 解析失败表示域名没有解析成地址。当前 `ENOTFOUND` 被归为 `configuration_error`，不在临时网络自动补样白名单；没有当时 VPN/DNS/endpoint 证据，不能进一步断言是断网或域名配置错误。
- 429 或断连已恢复，就不能用它作废后来的业务失败。`cleanup.startedAt` 之后的中止不能倒过来解释清理前的失败。
- 长尾要有阶段时钟和预算。按钮缺失、死锁、等待审批、模型反复选错、runner 卡住都能表现为超时，不能看超时二字就归网络。
- HTTP200 空响应、非法工具参数、摘要污染、候选被拒、任务未完成都不是网络补样理由。确定性计划内的 500/429/崩溃本来就是被测条件，不作废。
- 只有冻结规则认可且直接阻断的 live 外部失败才有界替补，当前每 Case 最多三轮。原样本、失败替补和映射全保留；预算耗尽仍不足有效样本，记外部环境阻塞。

不能开 Playwright retry、挑绿、扩大超时或改旧附件。发现分类器漏掉前置调用的真实网络原因，可以记录该外因和分类器限制，但不能手工伪造正式补样资格。

## 6. 常见第一处分歧速查

下表是排查经验，不是对新实验的预设结论。每次都回到冻结代码和样本。

| 现象 | 先核对什么，避免什么误判 |
|---|---|
| 找不到停止按钮 | 页面状态、pending 问题类型和耐久轮次；paused 审批与已结束轮次的普通追问不同。没有发出停止 HTTP 时不能归网络，见[冷审批说明](../bugfix/cold-approval-stop-control.md) |
| 摘要第一次 500、第二次 422 | 实际 Policy 允许的有界尝试和 fixture 是否错误拒绝合法第二次调用；计划内故障与替身自身拒绝分开 |
| 摘要被拒后还能答对 | 原历史可能仍在；检查真实替换、净收益、摘要独立事实及实际消费，不能判压缩已成功 |
| 摘要过长、污染、字段冲突 | 原候选、完整 replacement、前后同口径计量、Policy 清理；HTTP500 可能是本地压缩命令失败，不等于上游网关。旧输入首尾截取不等于删除 SQLite，见[设计取舍](../bugfix/compaction-summary-retry-budget.md) |
| 原始/最终工具正文不同 | 真实 selected 结果投影、callId/actionPlanId/ordinal、canonical 动作槽位及完整消息；不能只比较前缀或 flatten 后的文本 |
| 页面有额外过程报告 | 对应根 Turn 的模型/耐久来源、最后非空正文、真实 Markdown 和刷新；不把用户输入条数当报告条数 |
| 同批修改后读取 | 真实 ordinal、独占组和结算先后；跨轮查消费，同批不虚构中间请求 |
| PTC 程序返回常量也过了 | 变化输入在同一输出通道和结构位置是否变化；计数至少 0/1/多条，拒绝仅判空、跨位置搜数字、catch 后吞掉非法服务调用 |
| PTC 读成功却输出 null | 检查模型程序是否 return/console；嵌套真实结果与程序输出不同，不把程序遗漏输出判为工具丢数据 |
| Read 分片/重复搜索失败 | 按实际 offset/limit 和搜索范围核对完整业务覆盖及目标决策消费；允许只读复核，不以某个子集覆盖最终汇总 |
| 记忆一轮出现多次捕获 | 逐主模型 outcome、服务交换及 ADD/capture 来源绑定；不能固定每个用户 Turn 一次。先前合法保存与跨会话泄漏分开 |
| 副模型没有 failure 事件 | 查原响应、finishReason、私态与初始化时机；合法 abstain 不等于成功复核，`inferred_from_response` 不是耐久事实 |
| disabled 组件却有服务请求 | 核对当次 Mode/binding；当前禁用不能解释旧启用样本，也不能为了旧夹具重启已禁用组件 |
| `AGENT_LOOP_NONCONVERGENT` 后持续 `TURN_ALREADY_ACTIVE` | 查原 Turn 是否仍非终态及会话排水过程，不重复发送输入或清理日常状态库，见[会话阻塞说明](../bugfix/drain-nonconvergence-session-block.md) |
| 通知 admitted 未 claimed、父子互等 | 按实际锁/串行等待链查死锁。确认机制阻塞就登记，不能改成超时返回或禁止合法操作掩盖它 |
| `timing artifact does not match its contract` | Contract 与 timings 完整键集合、Driver 映射；修映射但不扩大预算、不补写旧成绩 |
| 夹具就绪 JSON 偶发为空 | 是否先写完临时文件再原子发布；文件存在不等于内容写完，属于夹具竞态 |
| 只有汇总称“轨迹完整” | 检查 manifest、complete 计数、外置事件和哈希；副模型未保存 messages 就仍缺证据，不能用主请求代替 |
| 合法工具响应回放失败 | 用同冻结适配器和完整原文；先验证编码/哈希，再区分模型、Provider、本地解析；新解析器不能重判旧成绩 |

领域审计中更细的调用关联和允许路径见[Web 技术方案](web-regression.md)。一般设计要求只在[设计准则](case-design.md)维护。

## 7. 追溯代码和建议跟进人

必须实际访问仓库，用本次冻结 suite 查 Case，用被测 master 查产品；不要只复制旧报告。分别记录最初真实设计、疑似缺陷引入、当前相关行作者及已有修复作者。独立文件注册可能晚于共享组件中的原始设计。

以下变量由本次计划填写；命令只读：

```bash
git -C "$REPO" log "$SUITE_SHA" --follow --format=fuller -- "$CASE_FILE"
git -C "$REPO" log "$SUITE_SHA" -S "$OLD_ID_OR_EXPRESSION" --format=fuller -p -- "$CASE_FILE"
git -C "$REPO" log "$SUITE_SHA" -G "$RELEVANT_REGEX" --format=fuller -p -- "$AUDIT_FILE"
git -C "$REPO" blame --line-porcelain -L "$START,$END" "$SUITE_SHA" -- "$AUDIT_FILE"
git -C "$REPO" blame --line-porcelain -L "$START,$END" "$MASTER_SHA" -- "$PRODUCT_FILE"
git -C "$REPO" show --format=fuller "$CANDIDATE_SHA" -- "$HISTORICAL_PATH"
git -C "$REPO" show "$MASTER_SHA:$PRODUCT_FILE"
git -C "$REPO" merge-base --is-ancestor "$FIX_SHA" "$MASTER_SHA"
git -C "$REPO" merge-base --is-ancestor "$FIX_SHA" "$SUITE_SHA"
```

`--follow` 一次一个文件，沿改名、旧 ID 和共享组件继续查；`-S/-G` 查实际判断表达式。blame 只说明当前行来自哪里，遇到格式化、搬迁或 merge 要继续看父提交。祖先检查返回 0=是、1=否，其他值是错误；非祖先仍可能有等价 cherry-pick，须比较补丁和实际实现。

保留完整 SHA、Git 原始作者名/邮箱、作者时间、文件/行和代码。没有二分复现时写“源码溯源线索，未证明最早缺陷引入”，不把 merge 作者或最后整行修改者自动当责任人。

已有修复但 master 未集成时，建议修复作者牵头适配/集成，原实现作者协助复核；组织分工无证据则待确认。纯模型/网络问题未定位仓库缺陷时，不虚构提交责任人。

## 8. 归因记录和报告

一次实验写一个 `analysis.json`，每个实际失败 Case 一条 finding，全部失败样本放在该 finding 的 `samples` 中，混合原因逐样本写。准备阶段阻断使用 `scope`，另保留未执行清单。当前报告脚本能渲染这些字段，但不会替你完成因果判断。

| 字段 | 填什么 |
|---|---|
| 顶层 `state/findings/contributions/nextActions` | 分析完成度、问题集合、实际贡献、按优先级的后续动作；state 不替代门禁 verdict |
| `caseId/category/mechanismState/firstDivergence` | Case 概要、主类、机制状态、可定位的首个分歧 |
| `samples[]` | `profile/ordinal/repeatEachIndex/category/firstDivergence/evidence/processesStopped/knownLimitations`；另记样本目录/键与原始/替补/第六样本身份 |
| `evidence/confidence/impact` | 真实证据路径、把握程度、用户影响；链接尽量相对实验根 |
| `sourceEvidence[]` | `{path,file,line,revision,code}`：证据文件、源码位置、真实版本及片段 |
| `caseProvenance` | `earliestDesignCandidate/defectIntroducedBy/currentLineAuthor/firstCaseRegistration`，另用 `limitation` 解释未二分、旧 ID/改名等边界 |
| `productProvenance` | 按问题域分组，每组 `file/masterLines[{line,author}]/earliestSourceTrace/repairNotInMaster`，关联实际逻辑、规范和集成检查 |
| `ownership[]` | `{scope,suggestedOwner:{name,email},role,basis,status}`；作者事实与建议分工分开 |
| `suggestedFix/nextAction` | 具体改哪里、为什么、单元/集成/Web 正反路径如何验证 |
| 顶层 `contributions/nextActions` 项 | 分别用 `{item,evidence,references}`、`{priority,action,references}`，关联真实台账 |

提交对象使用 `{sha,author,email,authorTime,subject}`；`evidence` 与 `references` 是路径字符串数组，方便报告生成链接。`suggestedValidation` 按“问题域 → unit/integration/web → 验证描述”组织。字段未知时写 null/空数组并解释，不能填伪 SHA。需要更细时可附 `taskContract`（题面原文与用户合同）、`externalDecision`（外因及补样判定）、`suggestedValidation`；关键结论也要写进展示字段，不能只藏在扩展 JSON。同一失败样本主因只计一次，次因不重复加到总数。

HTML 首页只展示独立 Case 总数、两路数量/占比、失败/成功、失败率、未完成数、原始样本数及两路/总体门禁。正文重点是全部失败 Case、违反什么、证据、代码来源、跟进人与验证建议。成功/未执行/排除全清单、耗时配置和补样映射放 JSON。预登记第六样本不增加 Case 数；归因不改原判分。

## 9. 报告完成前检查

即使正式校验因 FAIL 早退，也继续只读核对全部初始与替补结果：

- JUnit 的 failure/error/skipped、Case 和样本身份，与 findings/samples 一一对应；附件存在且可读，canonical 与哈希副本一致。
- 成功样本 audit/timings/model/settings 满足同冻结契约；失败诊断、trace、服务日志齐全。不能凭没有失败诊断推断 PASS，不能补造正式摘要。
- `trajectory.jsonl.gz` 的 manifest、样本号、complete 计数、外置正文及 processesStopped 一致。清理边界之后的事件单独解释。
- 进程强杀、停止失败及提前异常退出按实际记录；逐文件 SQLite 导出不是跨库原子快照。只清理任务持有的进程，不操作 8088。
- 原始/替补映射、源码归档、evaluated tree、日志和压缩包可读。检查已知密钥泄漏时只输出路径/计数，不打印密钥；命中则不能宣称可安全分享。

使用本次冻结报告器生成最终报告，然后生成 SHA256 清单封存：

```bash
node "$RUN_ROOT/runner/weekly-report.mjs" "$RUN_ROOT"
```

已封存实验只读，后续修订用新目录关联旧证据；不改已 hash 的报告或删除历史实验。贡献区分体系能力和真实产品修复；撤销/待确认问题、Case 修订、模型质量问题不计产品修复，Case 数不当架构覆盖率。

## 10. 归因之后做什么

只要求分析/周门禁时，交付归因和建议，不自动修 Case/产品或推送。获准修复后才进入“分析 → 修改 → 正反控制 → 新冻结样本 → 台账”的闭环；一个 Case 一个提交，产品 Bug 独立提交，纯文档整理集中一次。Case 修订向 `devops/regression-test` 交付；产品修复另从 master 开分支，带必要产品测试向 master 交付，不带整个套件，见[分支约定](harness-evaluation.md#4-分支与交付方式)。现阶段已有上游模型问题只登记。

取样和止损统一见[设计准则第 5 节](case-design.md#5-什么叫稳定什么叫全量通过)。涉及 `src/kernel/**`、`spec/**` 须事前确认具体范围和目的；Case 工作不擅改存储层。遇到需要这些修改的阻断，保留证据交人工处理，不能削弱断言绕过。
