# 职责、依赖与模式装配

本文件是规范性文件。适用范围、术语及变更规则见[规范入口](README.md)。

<a id="bnd-01"></a>

## BND-01 核心保持领域无关

公开契约只能包含类型、协议与基础语义；运行内核只能包含跨模式执行不变量。公开契约、运行内核和宿主不得定义具体扩展领域的数据结构、命令或模式特判，包括目标和规划；不得仅为一个具体功能新增核心枚举、决策点或可执行回调。宿主通过通用包目录装配具体扩展，不解释其业务数据。

仓库内的依赖方向必须满足下表；外部模型适配器、具体存储实现和界面框架不得反向进入公开契约或运行内核。

| 责任层 | 可以依赖的仓库模块 | 禁止事项 |
|---|---|---|
| 公开契约 | 自身的类型、协议和基础语义 | 运行内核、宿主、具体扩展、界面。 |
| 运行内核 | 公开契约、自身实现 | 具体工具、策略、提示词、宿主外部适配和界面。 |
| 领域扩展 | 公开契约、本领域实现、符合 BND-03 的共享协议与基础库，以及按 BND-05 声明依赖的公开契约 | 运行内核、宿主、其他领域的内部实现与私有类型、界面实现和装配目录；不得提供前端组件、样式或可执行渲染代码。 |
| 宿主 | 公开契约、运行内核、扩展装配目录和外部适配 | 以业务模式分支替代通用装配，或解释领域私有数据。 |
| 界面入口 | 宿主公开操作、稳定交互协议及界面层自身实现 | 具体领域扩展的源码与类型、运行内核内部实现、核心数据库及策略私有状态。 |

<a id="bnd-02"></a>

## BND-02 源码按功能归属组织

一个领域可以拥有工具、策略、提示词、类型和领域存储，并复用领域内逻辑。同领域工具和控制器可以读取本领域策略的只读状态快照，无需先对外发布或另配读取服务；不能直接修改该快照或提交核心状态。跨领域独立性必须满足 [BND-05](#bnd-05)。扩展不得依赖运行内核、宿主、界面实现或装配目录。前端实现由界面层拥有；领域通过公共协议提供结果、公开展示数据和交互请求。界面可为公开数据提供专用呈现，不能承担领域决策，具体要求见 [EDGE-01](interfaces.md#edge-01)。

<a id="bnd-03"></a>

## BND-03 `common` 的边界

`extensions/common` 是收纳目录：小工具、小策略按类型放置；共享代码按明确语义命名，例如执行限制、工具定义辅助、扩展自有文档更新。已有领域归属的内容留在领域内；形成完整功能后可以整体迁出。不得建立从 `common` 统一激活组件的机制、共享可变策略状态或无边界的服务集合。执行限制协议及其无状态包装可以共享，但由具体工具安装并落实。

共享库必须拥有独立、明确的协议或基础设施职责，不得反向依赖使用它的领域，不得识别具体策略身份、持有多个领域的业务状态或编排它们的流程。不能仅因多个领域代码相似，就把它们的提示词、决策、状态机或领域模型抽到公共业务包；将这种耦合命名为 `common`、服务或公开接口不改变其性质。通用存储辅助可以协调底层写入，但各领域的数据所有权、格式解释和状态决策仍独立。放在 `common/tools` 或 `common/policies` 的独立组件也须遵守 [BND-05](#bnd-05)。

<a id="bnd-04"></a>

## BND-04 新机制必须证明其通用性

新增或扩展核心机制前，必须说明现有三类策略、工具契约或公共服务为什么不足，新增内容由谁拥有、如何仲裁、权限如何收敛、如何持久化和恢复。至少用一个不依赖原业务的独立例子验证机制；不能只把领域类型改成泛型名称就认为已经解耦。新增普通领域能力不要求创建新的核心机制。

<a id="bnd-05"></a>

## BND-05 领域默认解耦，协作依赖必须显式

未声明依赖的领域须独立装配、修改、替换和移除，不得要求其他领域同步修改源码、提示词或私有存储。确实需要另一扩展能力的组件，可以声明对其公开契约的必需依赖；若组件在提供方缺席时仍能独立工作，也可以声明可选依赖。必需依赖缺失时不能装配；可选依赖缺失时不得执行对应协作、隐式安装或猜测替代工具的结果格式。两者都不能反向要求提供方依赖使用者。既有轮次仍按 [MOD-03](#mod-03) 和 [COMP-02](compatibility.md#comp-02) 验证历史绑定。

依赖由扩展包按消费组件声明提供方的组件类型、包标识、精确公开版本和组件标识。只检查模式实际选择的消费组件；未选择的兄弟组件不能增加依赖。所有必需提供方必须由模式显式选择；缺失、版本不匹配、重复声明、自依赖和循环依赖在装配时拒绝，不自动安装。可选提供方在场时同样校验精确版本及依赖循环，不能把不兼容当成缺席；原始声明和实际解析结果都必须进入绑定。策略描述中的 `requires` 同样是显式必需依赖，保留既有组件版本范围校验；影子策略不能满足活动策略的依赖。两类声明都必须进入绑定材料。

跨领域耦合限于提供方明确约定的稳定入口：协议类型、常量、公开数据及获准的服务调用。使用者须遵守该公开契约的版本、授权、错误及恢复规则。声明依赖不授予服务权限，不指定执行顺序，不允许读取其他领域未约定的内部状态、调用内部实现、直接写入对方存储或绕过内核效果提交。状态读取以领域所有权和约定为边界，不强制所有读取都经公开事件或新增权限服务；上下文提供快照不代表其中所有字段都是跨领域接口。不能通过重导出、公共业务包、宿主回调或宽泛服务注入隐藏依赖。

通过通用效果仲裁、共享基础协议或获准的复合工具调用可以协作而不依赖具体领域身份；分别遵守 [POL-03](policies.md#pol-03)、[BND-03](#bnd-03)、[ACT-01 / SVC-01](execution.md#act-01)。若代码按某个提供方的身份或业务字段作决策，则须声明该公开契约依赖，不能以“没有直接导入”代替声明。模式只选择组合和授权，不编排多个领域的私有业务。

解释工具领域结果时，必须使用实际执行定义的包、精确版本和组件身份；模型可见名称不能代替来源。作用域内的同名替换不继承被替换者的身份。没有可验证来源的历史结果不能被猜测为某个领域的公开结果。来源须随工具契约和执行事实保存，恢复仍校验绑定。

相对排序与依赖是独立声明；仅指定 `before/after` 不要求对方存在，指定必需依赖也不改变模式执行顺序。新增普通领域功能仍不应要求无依赖关系的领域同步修改。公共契约变化必须明确兼容影响并验证提供方、依赖方及无关领域。

<a id="mod-01"></a>

## MOD-01 声明才激活

模式配置逐项选择提示词、工具、技能来源、子智能体边界，以及策略的包、精确版本、组件、参数、授权、顺序和失败模式。包目录只表示“可用”，注册或导入不得激活同包兄弟组件；宿主、全局设置和界面不得另设隐式激活列表。模式从配置发现，不维护固定产品标识枚举。必需组件也须显式声明并校验。

<a id="mod-02"></a>

## MOD-02 装配必须可校验

未知组件、版本不匹配、非法配置、重复身份、独占所有权冲突、不合法顺序和未获准的服务请求必须在装配时失败；装配中途失败须释放已创建的资源。缺少宿主交互适配器不得静默删除模式已选工具：保留工具契约，调用时报告明确的服务不可用错误；不得假造成功或进入无法退出的业务状态。

<a id="mod-03"></a>

## MOD-03 绑定可追溯

每轮开始前必须持久化完整的 `TurnBinding`：策略契约与配置、工具及包来源、公共服务及授权、模型与适配器版本、提示词、模式、技能来源、权限及整体摘要。轮内动态能力必须先记录来源、版本及作用域，再用于后续步骤；不得改写初始绑定。恢复必须验证所需契约，不能把当前默认配置冒充历史绑定。

<a id="mod-04"></a>

## MOD-04 产品组合留在模式

当前标准模式显式装配规划能力，不装配目标能力；目标能力通过独立模式装配。新增产品组合由配置与扩展表达，不新增运行内核中的产品分支。具体完整组件表以对应模式配置为准，不在本规范复制。
