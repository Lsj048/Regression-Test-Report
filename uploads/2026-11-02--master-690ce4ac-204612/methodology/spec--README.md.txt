# 开发规范

`spec/` 是本仓库实现、代码审查和行为验收的规范入口。开发约束由本目录中的规范性文件直接定义，不需要从产品介绍、设计说明、评审描述或其他叙述性材料推导。

设计同时要求[核心保持领域无关](boundaries.md#bnd-01)、[不同领域独立演进](boundaries.md#bnd-05)、[界面与领域分离](interfaces.md#edge-01)及[数据唯一归属、避免重复保存](persistence.md#data-06)。领域内部内聚、允许复用；领域之间解耦，不能仅以目录分开或没有直接导入作为达标依据。展示与交互复用已有事实，不能为了界面方便再维护一份业务数据。

## 生效范围与判定规则

- 本目录约束跨模式的核心执行、扩展契约、装配、权限、持久化、恢复以及界面和子智能体边界，适用于所有入口和第一方、第三方扩展。
- “必须”“不得”是验收条件；“可以”表示在其他约束仍满足时允许的选择；“应”允许有明确理由且不破坏强制条款的替代实现。
- 本文件、下列主题文件及 `acceptance.md` 均为规范性文件。`conformance.md` 只记录当前证据、未覆盖部分和实现差距，没有修改或豁免要求的效力。
- 每条要求只有一个定义位置，其他文件按编号引用。条款同等生效，不能通过任选一份文件忽略其他约束；发现冲突时必须先明确并修正规范，不能按文件顺序或当前实现自行决定。
- 目录外的说明性文档只能解释或引用规范，不能增加、覆盖或放宽这里的开发约束。尚未明确的领域需求应先写成规范变更，不能把愿景或例子当成强制要求。
- 代码表达实现，公开类型表达数据结构，测试提供验证证据；三者都不因已经存在就自动成为正确的行为定义。不能仅为适配现状而降低规范要求。
- 文档拆分与移动不改变要求编号或语义。具体目录、类名和算法可以演进，但须满足相关条款及历史兼容要求。

已安装的扩展实现属于受信任代码。本规范不承诺对恶意扩展进行进程或安全沙箱隔离。发行组合的在线安装、社区市场、自进化和学习机制未在本目录定义，不属于当前规范的交付范围；新增时必须独立定义行为，并满足已有约束。

## 统一术语

| 术语 | 本目录中的定义 |
|---|---|
| Agent（智能体） | 使用模型和工具执行任务的实体。 |
| Tool（工具） | 拥有可执行能力及其模型契约、结果和执行语义的组件。 |
| Skill（技能） | 可加载的方法或知识资源，本身不授予执行权限。 |
| Policy（策略） | 通过规定接口返回结构化提案，由运行内核仲裁和提交的组件。 |
| Kernel（内核） | 包含公开契约、通用运行机制和宿主适配的核心部分；“运行内核”特指执行、仲裁、持久化协调及恢复机制。 |
| Host（宿主） | 统一装配模式、连接外部模型和存储，并提供核心操作的适配层。 |
| UI（用户界面） | 提交命令并展示公开事件与投影的可替换入口。 |
| Mode（模式） | 产品组合的激活声明。目录归属、包注册和组件激活互不等同。 |
| Session（会话） | 保存连续输入与历史的执行归属。 |
| Turn（轮次） | 消费一个触发输入的执行单元；暂停后可以恢复同一轮次。 |
| Step（步骤） | 轮次内的一次模型驱动推进。继续步骤不等于启动新轮次。 |
| Binding（绑定） | 组件、配置、权限和契约的可追溯快照。动态能力另外记录，不覆盖初始绑定。 |
| 事实与投影 | 事实是耐久保存的权威记录；投影是从事实构造的视图。流式显示、调试光标和缓存不是新的事实源。 |
| 幂等 | 同一操作重复提交或恢复，不额外产生消息、状态迁移或已确认的副作用。 |

代码标识符保持原名。每个主题首次涉及的专有协议须在正文解释；本目录不另建一份会与公开类型漂移的完整字段清单。

## 规范变更与验收

1. **定位要求。** 修改前列出相关条款和验收场景。保持行为的重构直接验证既有要求；行为变化须先明确触发条件、预期结果、失败方式、边界和兼容处理，再实现。
2. **保持唯一来源。** 在拥有该语义的主题中修改条款；新增独立领域时可以增加主题文件，并登记到索引。跨主题规则按编号引用，不复制正文。未确定的提议不得伪装成已生效要求。
3. **写可判定的要求。** 每条要求标明责任主体、适用条件和必须产生或禁止产生的结果；涉及错误、取消、并发、权限、持久化及恢复时，必须定义相应边界。示例只能帮助验收，不能替代规则。
4. **提供验证证据。** 每条要求至少关联一个验收场景。仲裁验证冲突与顺序；权限验证拒绝和嵌套；持久化验证关键提交间隙的恢复；界面验证对应的后端事实。随机模型回答或单纯的内部调用次数不能替代行为断言。
5. **保留强制约束。** 修改关键测试断言时，说明其对应的规范变化或测试错误；不得为通过检查删除权限、因果、持久化或恢复断言。新增核心机制遵守 [BND-04](boundaries.md#bnd-04)。
6. **同步状态。** 同一变更同时维护适用的规范、实现、测试和符合性记录。只有证据达到关闭条件才能关闭差距；存在差距时不能宣称对应部分完全符合。已关闭或撤销的差距移出当前清单，保留对应测试和当前验证边界，历史过程通过版本记录追溯，不在规范中累计修复流水账。不要求每次小改动建立全套提案模板或额外批准流程。

要求编号保持稳定，删除时保留变更说明，不将旧编号分配给其他语义。规范正文不维护实现进度、代码行号、测试数量或发布宣传；这些内容不得改变验收条件。
